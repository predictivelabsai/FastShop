# Phase 2C — Generated image provider seam

## Outcome

Generation-time imagery directions now resolve into concrete draft images. Newly
generated sites use a deterministic, theme-aware WebP placeholder provider by
default. It runs entirely in-process, makes no network requests and needs no
credentials. Existing sites are untouched; resolution runs only while applying a
new generated plan or when a merchant uses **Resolve imagery** in that generated
site's builder.

No database migration is required. Resolved bytes use the Phase 1a `SiteMedia`
table, and resolution metadata stays in `Site.settings_json.site_generation`.

## Provider protocol and selection

`app/site_images.py` defines the provider boundary:

```python
class SiteImageProvider(Protocol):
    def generate(
        self,
        direction: str,
        size: tuple[int, int],
        key: str,
    ) -> bytes | str: ...
```

Providers are registered by platform code with `register_image_provider`. The
operator selects a registered name through `FASTSHOP_IMAGE_PROVIDER`; the default
is `placeholders`. Provider choice is never read from a brief, page document,
merchant form or shopper request. An unknown configured name fails closed instead
of falling back silently.

Factories receive an `ImageProviderContext` containing only the site ID and the
validated design theme. The default `PlaceholderImageProvider` hashes the bounded
direction and stable block key, then draws a deterministic gradient and pattern
from the site's background, surface and accent colors. It returns image bytes;
it has no HTTP client and reads no secrets.

## Resolution flow and idempotency

`resolve_site_imagery` accepts at most 60 directions, matching the generation plan
bound. For each hero, split or product block it:

1. Locates the target page and block using tenant-and-site-scoped queries.
2. Preserves a nonempty image that no longer matches the previously resolved URL;
   manual media-library choices are never overwritten by a later resolve action.
3. Uses an approved `/static/...placeholder...` URL directly when the validated
   plan supplied one. Otherwise it calls the configured provider once for that
   unresolved target.
4. Validates provider bytes with the same file type, byte-size and pixel-count
   limits used by uploads, normalizes them to WebP, and upserts `SiteMedia` by a
   stable site/page/block storage key. Reapplying or retrying generation reuses the
   row instead of creating a duplicate. A changed direction updates that stable
   row.
5. Validates every resulting URL with `safe_url` and
   `content.validate_media_ownership`, then saves changed page documents through
   `content.save_page`. A cross-site `/site-media/` result is rejected.

Provider-returned HTTPS image URLs are registered in the site's media library.
Provider-returned site-media URLs must already belong to that site. Approved static
placeholder URLs remain direct static references and do not require a blob row.
All work is transactional: an invalid result rolls back the generated site or the
explicit editor action.

Plan application resolves imagery only after the generated pages, theme and
direction metadata exist and before commit. The explicit builder action uses CSRF,
the existing optimistic site lock, post-redirect-GET and builder change history.
It is available only when the site contains generation imagery metadata.

## Media library integration

Generated bytes appear in `/admin/sites/{site_id}/media` as normal site-owned
assets. Their title begins with `Image direction ·`; the media card also shows the
complete retained direction from generation metadata. `localized_alt` comes from
the target block's localized alt map, or from the direction when the block has no
useful alt. The default-locale `alt` remains available to the existing storefront
renderer and picker.

After resolution, merchants can use the Phase 1a picker normally. Referenced-delete
protection is unchanged because blocks contain the canonical `/site-media/` URL and
the existing reference scanner sees it in page drafts, revisions and builder
history.

## Adding a real provider

Add a provider module under `app/integrations/` and keep the transport and vendor
SDK inside that boundary. The implementation must:

- implement `generate(direction, size, key) -> bytes | str`;
- enforce a finite request timeout, response byte limit and one result per call;
- use `key` as the upstream idempotency key when the vendor supports it;
- return only supported image bytes or a safe HTTPS/site-owned URL;
- never log the direction together with credentials, response authorization data,
  signed URLs or raw provider errors containing secrets;
- register a short operator-controlled name at application startup.

Credentials belong only in operator environment configuration. For a site-scoped
provider, derive an uppercase identifier from `ImageProviderContext.site_id` and
read a variable such as `FASTSHOP_IMAGE_<SITE_ID>_API_KEY`, following the existing
per-site Stripe-key pattern. A platform-wide credential may use a provider-specific
`FASTSHOP_IMAGE_<PROVIDER>_API_KEY`. Never accept keys in briefs, page documents,
generation plans, merchant forms or provider directions, and never persist them in
`settings_json` or logs. Do not add a real network provider without separate retry,
quota, timeout, redaction and operator-readiness coverage.

## Offline evals

`python -m evals.site_generation` still runs both guided and mocked-plan modes for
ten golden briefs without network access. In addition to structure, menus, safety,
theme and draft application, it now asserts that:

- every visual block resolves to an owned `/site-media/` URL or an approved static
  placeholder;
- every owned URL passes `validate_media_ownership`;
- each run stays at or below the 60-image cap;
- a second resolution makes zero provider calls and creates no media rows.

The JSON and Markdown reports are written to `output/evals/`.

  retry/backoff policy for a real provider.
- Add image focal-point and crop metadata if future providers need art direction
  beyond the current three bounded output sizes.
- Consider explicit merchant regeneration/replacement controls only after the
  provider has cost and review safeguards; the current action fills missing images
  and preserves manual choices.
